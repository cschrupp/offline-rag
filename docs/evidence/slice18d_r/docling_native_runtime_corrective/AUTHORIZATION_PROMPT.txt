## 1. Incident and confirmed root cause

The Seneca H1/H2 review VM successfully received uploaded PDF bytes but failed at the document ingestion stage.

The durable error was:

- `code: ingest_failed`
- `reason: internal_ingest_failure`
- `parsed_artifacts_generated: 0`
- `parsed_searchable_document_count: 0`

Two attempts failed: one with five documents and one with a single 184,610-byte PDF.

Direct reproduction using Seneca's canonical `DoclingPdfParser` established the underlying exception:

`ImportError: libxcb.so.1: cannot open shared object file: No such file or directory`

The exception occurred during initialization of Docling's TableFormer model when `docling_ibm_models` imported OpenCV (`cv2`).

The failing environment was:

- Debian GNU/Linux 13 (trixie)
- Python 3.14
- Docling 2.126.0
- Docling Core 2.104.0
- Docling Parse 7.23.1
- OpenCV 5.0.0
- OCR disabled
- Provisioned Docling models at `/models/docling`
- Existing CPU-release Docker image

`ldd` identified these unresolved shared libraries:

| Library | Debian package |
|---|---|
| libxcb.so.1 | libxcb1 |
| libGL.so.1 | libgl1 |
| libglib-2.0.so.0 | libglib2.0-0t64 |
| libgthread-2.0.so.0 | libglib2.0-0t64 |
| libXext.so.6 | libxext6 |
| libX11.so.6 | libx11-6 |
| libSM.so.6 | libsm6 |
| libICE.so.6 | libice6 |

Installing these packages manually in the existing review container resolved all observed native dependencies.

Follow-up checks passed:

- No remaining `ldd` missing-library entries for the tested OpenCV shared objects.
- `import cv2` succeeded.
- TableFormer `TFPredictor` import succeeded.
- The user subsequently uploaded the original PDF through Seneca and obtained a grounded-looking answer with the source visible in the Evidence panel.

Therefore, the defect is in Docker runtime packaging, not OpenRouter, PDF validity, or the accepted scientific pipeline.

The manual installation is an operational workaround, not a reproducible release fix.

## 2. Required Dockerfile corrective

Inspect `deploy/Dockerfile`.

The final `runtime` stage currently installs `ca-certificates`, with compiler packages conditionally installed for the CUDA development profile.

Modify this stage to install the required native libraries for the CPU-release image.

Requirements:

1. Use Debian 13-compatible package names.
2. Install only the packages justified by the observed missing-library evidence and dependency closure.
3. Preserve the existing CPU/CUDA dependency-profile contract.
4. Keep `--no-install-recommends`.
5. Clean `/var/lib/apt/lists`.
6. Preserve non-root UID/GID 10001.
7. Preserve the application configuration, model mount contract and execution entrypoint.
8. Do not install generator runtimes or model weights in the image.
9. Do not change the Python dependency resolution or lockfile.

The runtime-stage package set must cover `libxcb1`, `libgl1`, `libglib2.0-0t64`, `libxext6`, `libx11-6`, `libsm6` and `libice6`, whether through explicit declarations or a demonstrably stable dependency closure.

Do not replace the OpenCV wheel or disable Docling table extraction to evade the missing dependencies.

## 3. Add a deterministic native-runtime qualification

Create a small project-owned container verification mechanism, placed consistently with the existing repository scripts and testing conventions.

It must operate on the actual final release image, not only the Python builder stage.

Required checks:

**A. Native linkage**

Inspect OpenCV's packaged shared objects and fail if `ldd` reports any `not found` dependency.

The check must have meaningful exit status. An empty `grep` result must not accidentally suppress errors or create a false PASS.

**B. Runtime imports**

Execute with the image's installed Python environment:

- `import cv2`
- import `TFPredictor` from `docling_ibm_models.tableformer.data_management.tf_predictor`

Both must succeed.

**C. Image identity and contract**

Confirm:

- CPU dependency profile.
- Correct `org.opencontainers.image.revision` label.
- Non-root runtime user.
- Unchanged runtime entrypoint and model/data mount conventions.
- No accidental inclusion of external secrets or private files.

A test that passes only because the developer's host already has the native libraries is invalid. The verification must exercise the packaged container itself.
